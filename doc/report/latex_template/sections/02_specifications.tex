\section{Requirements specification}
\subsection{Application scope}


The NEO-Watch project involves developing an application that allows users to analyze data on near-Earth objects provided by NASA. The application is designed to let users view available information on NEOs, search for specific objects, and track them more easily using customized features.

\vspace{0.25cm}

To meet these objectives, NEO-Watch includes a user account management system and a personal dashboard where each user can access their own information. The application also offers a search function for NEOs in its database, as well as the ability to create and edit a favorites list. Users can also add specific NEOs to the database and set up alerts based on the information that interests them.

\vspace{0.25cm}

The scope of the project is thus defined around three main areas: access to NEO data, searching for NEOs, and customization for each user. The various features designed to meet these objectives will be detailed in the following sections of the specifications, along with how those features will  choices selected by the group.

\subsection{Open questions and design choices}

\subsection{Feature description}

The first functionality of NEO-Watch concerns user management and access to the application. The application will provide a secured access system based on user accounts. A regular user will be able to create an account and log in to access the application's features and their personal space. Administrators will have additional permissions, allowing them to manage user accounts, consult connection history and trigger a data update. An administrator will also have access to the regular features of the application, while benefiting from these additional management capabilities.


\vspace{0.25cm}


Once connected, the user will have access to a personalized dashboard providing an overview of the most relevant information available in NEO-Watch. It will notably present upcoming close approaches, potentially hazardous NEOs among these approaches, and the object expected to come closest to Earth over a given period. The dashboard will also take the user's preferences into account by displaying information related to their favourite NEOs. The objective is to provide the user with a quick overview of the current situation without requiring them to perform a search each time they use the application.


\vspace{0.25cm}

The application will also provide a browsing and search system allowing users to explore the NEOs available in the database. Several search criteria will be available, such as the name or identifier of an object, its dimensions or the date of its next close approach. The results will be sortable according to different criteria in order to make it easier to find the most relevant objects. By selecting a NEO, the user will be able to access a more detailed view containing its relevant characteristics and information about its close approaches to Earth. Search results will also be exportable, allowing users to keep or further process the information obtained from the application.

\vspace{0.25cm}

NEO-Watch will additionally allow users to create NEOs in the application's database. This feature is intended to give users the possibility of adding an object they have observed when it is not already available in the data used by the application. These user-created objects will be kept separately from the data provided by NASA so that they remain available when the database is subsequently updated. This functionality therefore allows the database to contain both information originating from NASA and objects added directly by NEO-Watch users.

\vspace{0.25cm}


Another important feature of the application will be the management of a favourite NEO list. Users will be able to add or remove objects from their personal list and consult it at any time. The application will keep historical information about the distance of these favourite objects from Earth, making it possible to monitor their evolution over time. This history will also be used to produce graphs that can be exported by the user, providing a more visual way of following the objects they are interested in.


\vspace{0.25cm}

Finally, users will be able to create personalized alerts based on information concerning NEOs and their close approaches. For example, a user could request to be notified when an asteroid exceeding a given size passes within a specified distance of Earth. The application will regularly check the available data against the criteria defined by the user and store the corresponding notifications. These notifications will then be displayed when the user logs in, allowing them to quickly identify events matching their interests.


\vspace{0.25cm}

There will also be a feature that would provide users with additional information about the NEOs contained in the database, such as the distribution of their sizes, the proportion of potentially hazardous objects or the number of close approaches over a given period. The statistics would be presented in a way that makes them easy to interpret and relevant to the information available in NEO-Watch.

\vspace{0.25cm}

Moreover, NEO-Watch’s database will be automatically reloaded. NEO-Watch will already provide administrators with the possibility of manually updating the application's data. The optional functionality would extend this mechanism by allowing the update process to be performed automatically on a regular basis. This would reduce the need for an administrator to manually maintain the database and would help keep the information used by the application up to date.


\vspace{0.25cm}


Finally, the app will give “the NASA Astronomy Picture of the Day” to the user. Users will be able to access the picture provided by NASA through its dedicated API. Although this feature is not directly related to the monitoring of NEOs, it provides a more general and engaging astronomical experience. It also gives users the opportunity to discover another aspect of NASA's available data alongside the information provided by NEO-Watch.

\subsection{Questions and choices}

This section presents the choices made about the data source, the imported
data and the update policy. The way the data is split into tables, the
identification of objects, the protection of user-created NEOs and the
storage of statistics follow from these choices and are detailed in
Section~\ref{sec:mpd}.

\subsubsection{Choice of the API entry point}

The NASA NeoWs API offers three entry points: \texttt{/neo/browse}, which
lists all the NEOs; \texttt{/feed}, which gives all the close approaches
within a period; and \texttt{/neo/\{id\}}, which shows all the details about
an object. One page of \texttt{/neo/browse} shows at most 20 NEOs. As more
than 60,000 NEOs are registered, browsing the catalog requires 3,114 calls,
and since each object has an average of 29 approaches, this represents about
1.8 million rows. Moreover, \texttt{/neo/browse} is organized by NEO, whereas
F2, F3 and F6 work by period  : each such request would require reading the
whole catalog to extract a few approaches.

We therefore decided not to use \texttt{/neo/browse} and to keep only
\texttt{/feed} as the source of our database. It is completed with
\texttt{/neo/\{id\}} when a user marks a NEO as a favorite. The consequence
of this choice is that we will never have access to the full catalog : a NEO
that is far from Earth during our import will not be present in our
database. The application focuses only on close objects, not on small
objects or those too far away.

\subsubsection{API limits and import cost}

Filling the database has limits and a cost. With one key, we can make 2,000
requests per hour. In addition, \texttt{/feed} limits the period of a
request to a maximum of seven days; beyond one week, a 400 error is raised.
Filling a three-year database requires about 157 calls (1,096 days divided
by 7), whereas \texttt{/neo/browse} would have required 3,114 calls. We also
decided that each group member will use their own key rather than a single
shared key : running many imports during development will probably require
more requests than one key allows, and would therefore block the other
members.

\subsubsection{Selection of the data used}

The API does not provide a precise diameter value, only a size interval. We
could have kept the mean of the minimum and maximum of the interval, but
since this number is not present in the data, we chose to keep only the
minimum value. This choice is more cautious, especially for F6: with an
alert such as ``more than 100 m wide'', we are sure that the NEO's diameter
is effectively greater than 100 m. The complete interval is shown on the
NEO's detail page, and the minimum value is used only for sorting and
filtering. For the same reasons of consistency, measurements are expressed
in kilometers (km) and kilometers per hour (km/h).

NASA gives each approach distance in kilometers, miles, lunar distances and
astronomical units. The lunar distance is the most understandable for an
inexperienced user, but the people we aim to reach are already passionate
about astronomy. Therefore, besides distances in kilometers, users can also
read them in astronomical units, which we do not store since they are
obtained by a simple division.

Finally, the number of potentially hazardous NEOs requested by F2 requires
no computation, as the API already provides the attribute
\texttt{is\_potentially\_hazardous\_asteroid}.

\subsubsection{Import window}

F2 asks for upcoming approaches, which pulls towards the future, and FO3
asks for the evolution of the number of approaches, which pulls towards the
past. For F5, which requires the distance history of a favorite,
\texttt{/neo/\{id\}} returns all the approaches of the NEO in a single call,
without anything having to be imported. We import two years of past and one
year of future data. The past is imported once and considered frozen, with
no reason to be refreshed.

Since an object passes again on average every ten years, each NEO appears
only once in our window. A final restriction concerns the
nature of possible statistics. Any statistic about the evolution of a
characteristic over time is out of reach, and this is not a limitation of
the import window but of the model itself. What FO3 can offer is of another
kind : distributions over the population of objects in the database (size
distribution, proportion of potentially hazardous objects).

\subsubsection{Data updates}

Each daily update adds one day at the end of the one-year future window
(one call) and refreshes the next thirty days with the NEOs newly discovered
over that period (five calls in seven-day periods), which amounts to about
six calls per day. We do not purge: the volume involved is small and there
is no maintenance cost. A purge would also raise an integrity issue, since a
NEO referenced by a favorite or an alert cannot disappear.

F1 gives the administrator the responsibility of triggering updates, and FO7
proposes automatic triggering. We implement both: a daily batch process and
a button in the administrator space that call the same service. An ongoing
import is signaled by a status in the \texttt{import} table.

\subsubsection{Export formats}

F3 requires an export of search results and F5 an export of distance
history. Tabular data is exported as CSV. These exports trigger no call to
NASA : a favorite's history was retrieved when it was marked as a favorite
and lives in the database.

\subsubsection{NEOs creation by users}

One of the crucial points about being able to create NEOs, is that many users could create a NEO according to one recently observed. But we do not want a lot of creation just for one real NEO. In order to fix this, we chose that, to create a NEO a request has to be sent, and then an admin will accept it or not. By this process we also avoid some creations that could be made just as a joke for example.
Another point is how do we know if a NEO has been created by a user or not. In the class Neo, an attribute custom is present. It is used to know if a user or the NASA has referenced the object. But as the class Neo is linked with the class Proposal, we can also know who created the NEO if necessary.

This Proposal class is needed, when the user wants to add a NEO, he can propose his idea and he gives as much information as he can, after one admin will inspect it, and then accept or decline the proposal.

\subsubsection{Alerts}

The goal of this function is to send a notification according to the criteria the user has chosen. In order to do it, we need a criterion that will send the alert. According to the information available from the NASA API, we will have three criteria. The first one is if a NEO with a bigger diameter than a chosen value is detected, then if the NEO is closer than a maximum distance from an object like the Earth or Venus. Finally if a precise NEO, chosen by the user is detected. All of these can be combined together.
As the notification has to be sent when the user logs in, we can evaluate these criteria at this moment. Another option would have been to send the notification each time the database is updated, however it means that the user could be notified several times in one use which can be annoying for him if he needs to regularly update the database. There could be the same issue if this person logs in many times in a day but we can assume that usually people will use the application once or twice a day.
Moreover, one major problem about notifications, is that we do not want to send the same notification over and over. Once it has been sent, it has to be the first and last time. In order to do that, we could have saved all the notifications sent but with time, the table could become too voluminous. One way to answer this issue, is to save only the last criteria asked by the user, and delete it once it has been shown.

\subsubsection{Account}

As each admin has to be promoted by another admin, we obviously need to create by ourselves the first admin.  We can create a special id in the code, which has by default the admin status. And then, when a new admin is needed, the first one can upgrade an account to “admin”. When the new role is accepted, nothing changes except his permissions. An admin is also a user. He can do whatever a user can do, just he has the status of “admin” which provides him other functions to use.



Once an account has been deleted, his favourites and notifications are also deleted. However, the NEOs created by the user are kept in the table. As we assume that our user will be well informed, we suppose that their creations are useful and that is the reason why we want them to be still there.

\subsubsection{Optional features}

We chose to add three optional features to our app. The first one is FO3. It consists of providing some other statistics to the user. This one is important for us as we suppose that our users will be passionate about astronomy, and therefore, they will request more information about the NEOs.
Then we will add FO7. The principle is to update our database regularly. As this function already exists, but it has to be used manually, we want it to be automatic in case an admin cannot update it often enough.



Finally, our last choice was to choose FO8 which shows the picture of the day provided by NASA whenever the user wants. In fact, it does not provide any information, but it can be pretty pleasant for the user to see different pictures of our space as our users are probably here to inform themselves, seeing a new picture every day can push them to search about what they are looking for.

\subsection{Requirements and constraints}

\textbf{Technical}

\begin{itemize}
  \item Python 3.13, layered architecture imposed by the template (DAO / service / controller / view)
  \item Imposed stack: FastAPI (backend), Streamlit (frontend), PostgreSQL (database)
  \item Development environment: SSP Cloud / Onyxia, no local development
  \item Version control and collaboration via Git
\end{itemize}

\vspace{0.25cm}

\textbf{Subject-specific}

\begin{itemize}
  \item NASA API key quota (limited number of requests, to be anticipated especially for automatic updates)
  \item Preservation of user-created NEOs during automatic database updates
  \item Read-only access to the NASA API: no modification or write access on NASA's side, only NEO-Watch's own data (accounts, added NEOs, alerts, favourites) can be modified
  \item Data freshness: alerts and the dashboard depend on regular updates, which constrains how often synchronization with the API must occur
\end{itemize}
