\section{Requirements specification}
\subsection{Application scope}


The NEO-Watch project involves developing an application that allows users to analyze data on near-Earth objects provided by NASA. The application is designed to let users view available information on NEOs, search for specific objects, and track them more easily using customized features.

\vspace{0.25cm}

To meet these objectives, NEO-Watch includes a user account management system and a personal dashboard where each user can access their own information. The application also offers a search function for NEOs in its database, as well as the ability to create and edit a favorites list. Users can also add specific NEOs to the database and set up alerts based on the information that interests them.

\vspace{0.25cm}

The scope of the project is thus defined around three main areas: access to NEO data, searching for NEOs, and customization for each user. The various features designed to meet these objectives will be detailed in the following sections of the specifications, along with how those features will  choices selected by the group.

\subsection{Open questions and design choices}

\subsection{Feature description}

The first functionality of NEO-Watch concerns user management and access to the application. The application will provide a secured access system based on user accounts. A regular user will be able to create an account and log in to access the application's features and their personal space. Administrators will have additional permissions, allowing them to manage user accounts, consult connection history and trigger a data update. An administrator will also have access to the regular features of the application, while benefiting from these additional management capabilities.


\vspace{0.25cm}


Once connected, the user will have access to a personalized dashboard providing an overview of the most relevant information available in NEO-Watch. It will notably present upcoming close approaches, potentially hazardous NEOs among these approaches, and the object expected to come closest to Earth over a given period. The dashboard will also take the user's preferences into account by displaying information related to their favourite NEOs. The objective is to provide the user with a quick overview of the current situation without requiring them to perform a search each time they use the application.


\vspace{0.25cm}

The application will also provide a browsing and search system allowing users to explore the NEOs available in the database. Several search criteria will be available, such as the name or identifier of an object, its dimensions or the date of its next close approach. The results will be sortable according to different criteria in order to make it easier to find the most relevant objects. By selecting a NEO, the user will be able to access a more detailed view containing its relevant characteristics and information about its close approaches to Earth. Search results will also be exportable, allowing users to keep or further process the information obtained from the application.

\vspace{0.25cm}

NEO-Watch will additionally allow users to create NEOs in the application's database. This feature is intended to give users the possibility of adding an object they have observed when it is not already available in the data used by the application. These user-created objects will be kept separately from the data provided by NASA so that they remain available when the database is subsequently updated. This functionality therefore allows the database to contain both information originating from NASA and objects added directly by NEO-Watch users.

\vspace{0.25cm}


Another important feature of the application will be the management of a favourite NEO list. Users will be able to add or remove objects from their personal list and consult it at any time. The application will keep historical information about the distance of these favourite objects from Earth, making it possible to monitor their evolution over time. This history will also be used to produce graphs that can be exported by the user, providing a more visual way of following the objects they are interested in.


\vspace{0.25cm}

Finally, users will be able to create personalized alerts based on information concerning NEOs and their close approaches. For example, a user could request to be notified when an asteroid exceeding a given size passes within a specified distance of Earth. The application will regularly check the available data against the criteria defined by the user and store the corresponding notifications. These notifications will then be displayed when the user logs in, allowing them to quickly identify events matching their interests.


\vspace{0.25cm}

There will also be a feature that would provide users with additional information about the NEOs contained in the database, such as the distribution of their sizes, the proportion of potentially hazardous objects or the number of close approaches over a given period. The statistics would be presented in a way that makes them easy to interpret and relevant to the information available in NEO-Watch.

\vspace{0.25cm}

Moreover, NEO-Watch’s database will be automatically reloaded. NEO-Watch will already provide administrators with the possibility of manually updating the application's data. The optional functionality would extend this mechanism by allowing the update process to be performed automatically on a regular basis. This would reduce the need for an administrator to manually maintain the database and would help keep the information used by the application up to date.


\vspace{0.25cm}


Finally, the app will give “the NASA Astronomy Picture of the Day” to the user. Users will be able to access the picture provided by NASA through its dedicated API. Although this feature is not directly related to the monitoring of NEOs, it provides a more general and engaging astronomical experience. It also gives users the opportunity to discover another aspect of NASA's available data alongside the information provided by NEO-Watch.

We decided to not use /browse and keep only /feed as the source of our database. It will be completed with /neo/id when the user will mark a Neo as favourite.

The consequence of this choice is thqt we will never have access to the full catalog : a Neo being far from Earth during our import, will not be present in our database. The app focus only on close objects qnd not on little object, or the ones too far away.

Which informations can be used ?

The API does not provide a precise value of the diameter. We have only an interval of size. We could have choose to keep the mean between the minimum and the maximum of the interval. But as this new number is not present in the data, we chose to keep only the minimum value.

This choice is more cautious, especially for F6 : if we have an alert like "more than 100m large", we are sure that the diameter neo is effectively wider than 100m. We will provide the complete interval on the detailed page of the Neo. This minimal value will be used only for sorting or filter tasks. For the same reasons of homogeneity, mesures will be in Kilometers (km) and Kilemeters per hour (km/h).

We also asked ourselves about units of approach distance. The NASA gives each distance in kilometers, miles, lunar distance and astronomical unit. In fact, the lunar distane is the most understandable for an inexperienced user, but the people we aim to reach are already passionate about astronomy. Therefore, beside distances in kilometers, we will also be able to read it in astronomical unit without stocking it. We can get it just by a simple division.

How to know if the Neo is dangerous ?

F2 wants us to give the number potentialy dangerous. For this information, we do not calcul anything, there is already an argument is_potentially_hazardous_asteroid.

Cb de table ?

L’API renvoie pour chaque NEO une liste d’approches datées avec leur distance et vitesse : un même NEO apparaît plusieurs fois sur une même période. Une table unique aurait dupliqué les caractéristiques physiques à chacune de ces approches. Au-delà du volume le risque est celui de la mise à jour : le diamètre, la magnitude sont révisés par la NASA, il aurait fallu modifier 29 lignes.

Nous avons séparés en deux tables, neo et approche, reliées par une clé étrangère. L’argument décisif est l'intégrité référentielle : un favori, une alerte, porte sur un NEO et non une approche, et sans table néo ces relations n’ont aucune cible stable à référencer.

Quelle clé primaire pour un NEO ?

L’identifiant NASA garantit l’unicité mais F4 permet à un utilisateur de créer un NEO qu’il a observé, cet objet n’a par définition aucun identifiant NASA.

Nous utilisons une clé technique auto-incrémentée et conservons l’identifiant NASA dans une autre colonne nullable et contrainte unique. 

Comment protéger les neo créer par les utilisateurs ?

Un upsert écraserait à chaque import les objets saisis par les utilisateurs. Nous ajoutons à neo une colonne origine qui vaut NASA ou UTILISATEUR. L’upsert pour l’import porte une clause WHERE origin = “NASA”.

Par rapport à FO3 : nombre d’objets dangereux sur une période, distance minimale, moyennes.. Une table de statistiques précalculées rafraîchie à chaque import accélère l’affichage.

Sur quelle plage importons-nous ?

F2 demande les prochaines approches, ce qui tire vers le futur et F03 demande une évolution du nombre d’approches, ce qui tire vers le passé. Pour F5 qui demande l’historique des distances d’un favori, /neo/id renvoie en un seul appel l’ensemble des approches du NEO sans qu’il ait fallu importer quoi que ce soit.

Nous importons deux années de passé et une année de futur. Le passé est importé une fois et considéré comme figé, il n’a aucune raison d’être rafraîchi.

Un objet repassant en moyenne tous les dix ans, chaque NEO n'apparaît qu'une fois dans notre fenêtre. Le nombre d'approches par mois et le nombre d'objets distincts par mois y sont donc quasiment la même quantité : nous ne retenons qu'un seul de ces deux indicateurs. 
Une dernière restriction de ce choix porte sur la nature des statistiques possibles. Toute statistique portant sur l'évolution d'une caractéristique dans le temps est hors de portée, et ce n'est pas une limite de la fenêtre d'import mais du modèle lui-même. Ce que FO3 peut offrir est d'un autre ordre : des distributions sur la population des objets présents en base (répartition des tailles, proportion d'objets potentiellement dangereux).
Chaque mise à jour quotidienne ajoute un jour à la fenêtre et rafraîchit les trente prochains jours avec les nouvelles NEO découvertes sur ces temps, soit environ six appels.
Nous ne purgons pas : le volume concerné est faible et il n’y a pas de coût de maintenance. Une purge poserait un problème d’integrité comme une NEO référencé par un favori ou une alerte ne peut pas disparaître.

By this process we also avoid some creation that could be made just for the joke for example.
Another point is how do we know if a Neo has been created by an user or not. In the class Neo, an attribute custom is present. It is used to know if a user or the Nasa has referenced the object. But as the class Neo is linked with the class Proposal, we can also know who created the Neo if necessary.

	This Proposal class is needed, when the user wants to add a Neo, he can propose his idea and he gives as much information as he can, after one admin will inspect that, and then accept or decline the proposal.

F6, The Alert

The goal of this function is to send a notification according to the criteria the user has chosen. In order to do it, we need a criteria that will send the alert. According to the information available from the Nasa API, we will have three criteria. The first one is if a Neo with a bigger diameter than a chosen value is detected, then if the Neo is closer than a maximum distance from an object like the Earth or Venus. Finally if a precise Neo, chosen by the user is detected. All of these can be combined together.
As the notification has to be sent when the user logs in, we can evaluate these criteria at this moment. Another option would have been to send the notification each time the database is updated, however it means that the user could be notified several times in one use which can be annoying for him if he needs to regularly update the database.There could be the same issue if this person logs in many times in a day but we can assume that usually people will use the application once or twice a day.
Moreover, one major problem about notifications, is that we do not want to send the same notification over and over. Once it has been sent, it has to be the first and last time. In order to do that, we could have saved all the notifications sent but with time, the table could become too voluminous.One way to answer this issue, is to save only the last criteria asked by the user, and suppress it once it has been shown.

\subsection{Requirements and constraints}

\textbf{Technical}

\begin{itemize}
  \item Python 3.13, layered architecture imposed by the template (DAO / service / controller / view)
  \item Imposed stack: FastAPI (backend), Streamlit (frontend), PostgreSQL (database)
  \item Development environment: SSP Cloud / Onyxia, no local development
  \item Version control and collaboration via Git
\end{itemize}

\vspace{0.25cm}

\textbf{Subject-specific}

\begin{itemize}
  \item NASA API key quota (limited number of requests, to be anticipated especially for automatic updates)
  \item Preservation of user-created NEOs during automatic database updates
  \item Read-only access to the NASA API: no modification or write access on NASA's side, only NEO-Watch's own data (accounts, added NEOs, alerts, favourites) can be modified
  \item Data freshness: alerts and the dashboard depend on regular updates, which constrains how often synchronization with the API must occur
\end{itemize}


\subsection{Team work and organization}

The whole writing process of our intermediate report was based on a clear set of rules. Firstly, division of labor: everyone in the group contributed, with some members contributing more to certain sections based on differences in skill or familiarity with the topic. Every section not only had a writer but also a designated reviewer, ensuring that each part was checked by someone other than its writer, reducing the risk of errors or inconsistencies going unnoticed.

\vspace{0.25cm}

Beyond the writing itself, the group follows two rules meant to keep both the report and the technical work consistent from the start. The first concerns sequencing: section 2.2 ("Questions and Choices") is written before any other technical section, since it requires obtaining a NASA API key and actually querying the API to understand its real data structure, request quotas, and any missing or unexpected fields. Every other technical section, from the class diagram to the endpoint table, depends on this section, so starting elsewhere would risk having to rework and correct sections a second time.

\vspace{0.25cm}

The second rule concerns vocabulary. The team shares a reference document where naming decisions are fixed once and reused consistently throughout the project, for instance, choosing between "NEO" and "Asteroid," or "Approach" and "CloseApproach." These names must remain identical across the class diagram, the physical data model, and the API endpoints; inconsistent naming between different parts is one of the most visible issues an evaluator can spot, so agreeing on terminology in advance avoids this problem entirely.
